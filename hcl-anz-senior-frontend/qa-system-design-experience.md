## SD-01: RADIO Framework for Frontend System Design

**Q:** *"How do you approach a frontend system design question? Walk me through your framework."*

🇻🇳 **Giải thích chi tiết:**
Khi gặp câu hỏi system design trong phỏng vấn, mình cần một framework có cấu trúc để không bị lan man và cover đủ các khía cạnh. RADIO là framework phổ biến nhất cho frontend system design: Requirements, Architecture, Data Model, Interface, Optimizations. Bước đầu tiên là Requirements - mình phải hỏi lại interviewer để clarify functional và non-functional requirements, tương tự như khi làm dự án thực tế, khoảng 5-7 phút. Tiếp theo là Architecture - vẽ high-level component tree và data flow, chỉ ra các layer chính như App Shell, Page Layout, Feature Components, và Shared UI. Data Model là bước quan trọng nhất - mình cần định nghĩa state structure, API contracts, caching strategy, và làm sao để manage server state vs client state. Interface Definition là bước mình design component APIs, props interface, events, và communication giữa các components. Cuối cùng là Optimizations - đây là lúc mình show senior-level thinking: performance (lazy loading, code splitting, memoization), accessibility (ARIA, keyboard nav), error handling, và edge cases. Trong 25 phút interview, mình chia thời gian: 5 phút Requirements, 5 phút Architecture, 7 phút Data Model, 4 phút Interface, 4 phút Optimizations. Điều quan trọng là luôn vẽ diagram khi giải thích và hỏi ngược interviewer để show communication skill.

🇬🇧 **Sample Answer:**
> *"I use the RADIO framework for frontend system design questions, which gives me a structured approach to cover all important aspects within the time constraint. First, I spend about 5 minutes on Requirements - I ask clarifying questions about functional needs like core features, user roles, and data requirements, plus non-functional needs like performance targets, browser support, and accessibility standards. This is critical because assumptions can lead to a completely wrong design. Next, I move to Architecture where I sketch a high-level component tree showing the App Shell, routing layer, page components, and shared UI library. I identify the main data flow direction and communication patterns between components. For the Data Model phase, which I consider the most important part, I define the state structure - separating server state from client state, choosing appropriate state management tools, and designing API contracts with TypeScript interfaces. The Interface Definition step is where I specify component props, events, and the public API of each major component, thinking about reusability and composability. Finally, Optimizations is where I demonstrate senior-level thinking - I discuss code splitting with React.lazy, virtualization for large lists, memoization strategies, accessibility compliance, error boundaries, and edge cases like offline support or slow networks. For a 25-minute question, I typically spend 5-5-7-4-4 minutes across these phases, always drawing diagrams and checking in with the interviewer to make sure I'm addressing what they care about most."*

## SD-02: State Management Architecture

**Q:** *"How do you decide on a state management architecture for a complex application? What are the different categories of state?"*

🇻🇳 **Giải thích chi tiết:**
State management là một trong những quyết định architecture quan trọng nhất trong frontend. Mình chia state thành 4 loại chính: Local State (component-level, dùng useState/useReducer), Server State (data từ API, dùng TanStack Query/SWR), Global State (shared across components, dùng Zustand/Redux/Context), và URL State (route params, search params, dùng router). Sai lầm phổ biến nhất là đưa hết mọi thứ vào global store - điều này làm app phức tạp và khó maintain. Nguyên tắc của mình là "keep state as local as possible" - chỉ elevate lên khi thực sự cần. Với Server State, mình hầu như luôn dùng TanStack Query vì nó handle caching, background refetch, stale-while-revalidate, và optimistic updates. Ví dụ cụ thể với banking dashboard: account balances là Server State (cached 30s, background refetch), selected account là URL State (deep-linkable), transaction filters là URL State (shareable URLs), toast notifications là Global State (Zustand store nhỏ), và form inputs là Local State (useState). Cách tiếp cận này giữ cho architecture clean, testable, và scalable. Khi team grow, mọi người đều biết state nào ở đâu và tại sao.

🇬🇧 **Sample Answer:**
> *"I categorize application state into four distinct types, and each has its optimal management strategy. Local State is component-specific data like form inputs, toggle states, or UI flags - I use useState or useReducer for this. Server State is data that lives on the backend and needs to be synchronized - I strongly prefer TanStack Query because it handles caching, background refetching, stale-while-revalidate, deduplication, and optimistic updates out of the box. Global State is truly shared client-side state like user preferences, theme, or notification queues - I use Zustand for this because it's lightweight, has no boilerplate, and works well with TypeScript. URL State includes route parameters and search params, which I manage through the router because it makes views deep-linkable and shareable. For a concrete example, in a banking dashboard I'd architect it like this: account balances and transaction history are Server State managed by TanStack Query with a 30-second stale time and background refetching. The currently selected account ID goes in the URL as a route param so users can bookmark or share links. Transaction filters like date range and category also go in URL search params for the same reason. Toast notifications and modal states are Global State in a small Zustand store. Form inputs for transfers or payments are Local State within the form component. My guiding principle is 'keep state as local as possible' - I only elevate state when there's a concrete need, because premature globalization of state leads to unnecessary complexity, re-renders, and coupling between components."*

## SD-03: API Communication Patterns

**Q:** *"Compare REST, GraphQL, and gRPC for frontend communication. When would you choose each, and how do you handle real-time data?"*

🇻🇳 **Giải thích chi tiết:**
Mỗi API pattern có strengths riêng và phù hợp với use cases khác nhau. REST là standard phổ biến nhất - simple, cacheable (HTTP caching), tooling tốt, nhưng có vấn đề over-fetching và under-fetching khi UI cần data từ nhiều resources. GraphQL giải quyết vấn đề đó bằng cách cho client query chính xác những gì cần - rất tốt cho mobile (bandwidth thấp) và complex UI với nhiều nested relationships, nhưng trade-off là phức tạp hơn (schema, resolvers, caching phía client với Apollo/Relay). gRPC dùng Protocol Buffers, nhanh hơn REST/GraphQL về serialization, có type safety từ proto files, và hỗ trợ streaming - rất tốt cho internal services và real-time data, nhưng browser support cần grpc-web proxy. Với real-time data, có 3 lựa chọn chính: WebSocket cho bidirectional communication (chat, trading), Server-Sent Events (SSE) cho server-to-client one-way streaming (notifications, live feeds), và Long Polling cho fallback khi WebSocket không khả thi. Trong thực tế, mình thường dùng hybrid approach: REST cho CRUD operations cơ standard, WebSocket cho real-time updates (trading prices, notifications), và GraphQL cho dashboard phức tạp với nhiều data sources. Ví dụ ở Nano Trading: REST cho authentication và user settings, WebSocket cho live price streaming và order updates, và TanStack Query để bridge - WebSocket messages invalidate relevant queries để UI update.

🇬🇧 **Sample Answer:**
> *"Each API pattern serves different needs, and in practice I often use a hybrid approach. REST is my default choice for standard CRUD operations - it's well-understood, has excellent HTTP caching support, and the tooling ecosystem is mature. However, it suffers from over-fetching and under-fetching when the UI needs data from multiple related resources, which leads to waterfall requests. GraphQL solves this by letting the client specify exactly what data it needs in a single request - it's excellent for complex dashboards with nested data relationships and for mobile where bandwidth matters. The trade-off is added complexity with schema management, resolver implementation, and client-side caching through Apollo or Relay. gRPC uses Protocol Buffers for serialization, which is significantly faster than JSON, and it provides end-to-end type safety from proto file definitions. It's ideal for internal service communication and supports streaming natively, though browsers need a grpc-web proxy. For real-time data, I evaluate three approaches: WebSocket for bidirectional communication like chat or live trading where both client and server need to push data, Server-Sent Events for unidirectional server-to-client streaming like notifications or live feeds which is simpler than WebSocket and works over HTTP/2, and Long Polling as a fallback for environments where persistent connections aren't feasible. In my trading platform project, I used a hybrid: REST with TanStack Query for authentication, user settings, and historical data; WebSocket for real-time price streaming and order status updates; and I bridged them by having WebSocket messages invalidate relevant TanStack Query caches, so the UI always showed the latest data without manual synchronization. This gave us the simplicity of REST for standard operations and the performance of WebSocket for time-sensitive data."*

## SD-04: Design a Banking Dashboard (System Design)

**Q:** *"Design the frontend for an internet banking dashboard - like ANZ's online banking. Walk me through your full design."*

🇻🇳 **Giải thích chi tiết:**
Đây là câu hỏi system design điển hình cho ANZ interview. Mình sẽ dùng RADIO framework để approach. Requirements: Functional - user xem được tất cả accounts (savings, credit, loan), transaction history với filters, quick transfer, bill payments, và notifications. Non-functional - load time dưới 2s, WCAG 2.1 AA accessibility, bảo mật cao (session timeout, CSP, XSS prevention), responsive cho mobile/tablet/desktop, và hỗ trợ offline xem recent transactions. Architecture: App Shell pattern với top-level Auth Provider, Router (React Router), và Layout (Header với nav, Sidebar, Main Content). Core pages: Dashboard Overview, Account Detail, Transfer, Payments, Settings. Shared packages: UI components, API client, auth utilities, và analytics. Data Model: Server State (TanStack Query) cho accounts, transactions, payees - mỗi endpoint có stale time khác nhau (balances: 30s vì thay đổi thường xuyên, payees: 5min vì ít thay đổi). Client State (Zustand) cho selected account, UI preferences, notification queue. URL State cho current page, account ID, transaction filters. Component Tree: DashboardPage chứa AccountsOverview (list cards), QuickActions (transfer, pay), RecentTransactions (virtualized list), và SpendingChart. Mỗi component có error boundary riêng. Optimizations: Code splitting theo route (React.lazy), virtualization cho transaction list (react-window), skeleton loading states, optimistic updates cho transfers, Web Workers cho heavy calculations như spending analytics, và Service Worker cho offline caching basic account data. Security: JWT với refresh token rotation, CSP headers, input sanitization, và auto-logout sau 5 phút inactive.

🇬🇧 **Sample Answer:**
> *"I'll walk through this using the RADIO framework. Starting with Requirements: functionally, users need to view all accounts with balances, see transaction history with filtering and search, make quick transfers between accounts, pay bills, and receive notifications. Non-functionally, we need sub-2-second initial load, WCAG 2.1 AA accessibility compliance, strong security with session management, responsive design across all devices, and some offline capability for viewing recent transactions. For Architecture, I'd use an App Shell pattern with a top-level AuthProvider for session management, React Router for navigation, and a Layout component with persistent header navigation, collapsible sidebar, and main content area. The main pages are Dashboard Overview, Account Detail, Transfers, Payments, and Settings, each loaded via React.lazy for code splitting. I'd structure shared code as internal packages: a UI component library, a typed API client, auth utilities, and an analytics wrapper. The Data Model is where it gets interesting - I'd use TanStack Query for all server state with different stale times: account balances refresh every 30 seconds since they change frequently, payee lists cache for 5 minutes since they're relatively static, and transaction history uses infinite scrolling with cursor-based pagination. Client state in a small Zustand store handles UI preferences, notification queues, and transfer form drafts. The selected account ID and transaction filters live in URL params for deep-linking. For the Interface, the DashboardPage composes AccountsOverview showing card-style account summaries, QuickActions for common operations, a RecentTransactions virtualized list handling thousands of entries smoothly, and a SpendingChart with Web Worker-powered calculations. Each section has its own ErrorBoundary and loading skeleton. For Optimizations, I'd implement route-based code splitting reducing initial bundle by 60%, react-window virtualization for transaction lists, optimistic updates on transfers so the UI feels instant, prefetching of likely-next-viewed account details on hover, and a Service Worker caching strategy for offline access to basic account data. Security is critical for banking: JWT with refresh token rotation, Content Security Policy headers, strict input sanitization against XSS, automatic session timeout after 5 minutes of inactivity, and all sensitive operations require re-authentication."*

## SD-05: Design a Design System

**Q:** *"How would you design and implement a design system that serves multiple teams and applications?"*

🇻🇳 **Giải thích chi tiết:**
Design system không chỉ là component library - nó là một product phục vụ các developers khác. Foundation bắt đầu từ Design Tokens - đây là "single source of truth" cho colors, spacing, typography, shadows, breakpoints. Mình dùng JSON/YAML định nghĩa tokens, rồi generate ra CSS custom properties, Tailwind config, và Figma tokens đồng thời. Cách này đảm bảo designer và developer luôn sync. Component architecture phải theo Atomic Design: Atoms (Button, Input, Icon), Molecules (FormField, SearchBar), Organisms (Header, DataTable), và Templates/Pages. Mỗi component cần có: typed props với TypeScript, composition pattern (render props/children), controlled và uncontrolled modes, forwardRef cho DOM access, và full accessibility (ARIA attributes, keyboard navigation, focus management). API design là yếu tố quyết định adoption: mình theo principle "simple things simple, complex things possible" - default props cho common use cases, nhưng cho phép customization qua composition và polymorphic components (as prop). Versioning dùng semantic versioning (semver) và changelog tự động. Mỗi breaking change cần có migration guide và codemod. Documentation sử dụng Storybook với interactive examples, do's and don'ts, accessibility notes, và copy-paste code snippets. Rollout strategy: bắt đầu từ 1 pilot team, thu thập feedback 2-4 tuần, iterate, rồi mở rộng dần. Mình tạo adoption dashboard tracking component usage across apps để biết team nào cần hỗ trợ. Quan trọng nhất là treat design system như product - có roadmap, office hours, và feedback channel.

🇬🇧 **Sample Answer:**
> *"A design system is fundamentally a product that serves other developers, so I approach it with that mindset. The foundation starts with Design Tokens - a single source of truth for colors, spacing, typography, shadows, and breakpoints defined in a format like JSON. From these tokens, I generate CSS custom properties for runtime theming, Tailwind configuration for utility classes, TypeScript constants for programmatic access, and Figma tokens to keep designers synchronized. This means changing a primary color in one place updates everything automatically. For component architecture, I follow Atomic Design principles: Atoms like Button, Input, and Badge are the smallest units; Molecules like FormField and SearchBar combine atoms; Organisms like DataTable and NavigationHeader are complex composed components. Every component needs typed props with TypeScript generics where appropriate, support for both controlled and uncontrolled modes, forwardRef for DOM access, comprehensive accessibility with ARIA attributes, keyboard navigation, and focus management, and a composition-friendly API using children and render props rather than monolithic config objects. The API design philosophy is 'simple things should be simple, complex things should be possible' - I provide sensible defaults for common use cases while allowing deep customization through composition and polymorphic components using an 'as' prop. For versioning, I use semantic versioning with automated changelogs from conventional commits, and every breaking change ships with a migration guide and ideally a codemod that teams can run to auto-update. Documentation lives in Storybook with interactive examples, do's and don'ts, accessibility specifications, and copy-paste code snippets - not just API docs but real usage patterns. For rollout, I start with one pilot team for 2-4 weeks, collect feedback aggressively, iterate on pain points, then expand gradually. I create an adoption dashboard that tracks which components are used where, so I know which teams need support and which components need improvement. The key success metric isn't number of components - it's adoption rate and developer satisfaction."*

## SD-06: Micro Frontend Architecture Decision

**Q:** *"When would you recommend micro frontends over a monolithic frontend? What's your decision framework?"*

🇻🇳 **Giải thích chi tiết:**
Micro Frontend (MFE) là một architectural pattern chia frontend thành các ứng dụng nhỏ, độc lập, có thể develop và deploy riêng. Nhưng không phải lúc nào cũng cần MFE - nó có trade-offs đáng kể. Mình dùng decision framework dựa trên 4 yếu tố chính: Team Size (dưới 3 teams thì monolith đủ rồi, trên 5 teams với codebase lớn thì MFE có lợi), Independent Deployment (nếu các teams cần deploy độc lập với release cycles khác nhau thì MFE giúp), Technology Diversity (nếu có legacy app cần migrate dần dần hoặc teams muốn dùng tech khác nhau), và Organizational Structure (Conway's Law - architecture nên reflect tổ chức team). MFE có nhiều cách implement: Module Federation (Webpack 5/Rspack) cho runtime integration - tốt cho shared dependencies và hot updates, Single-SPA cho framework-agnostic orchestration, iframe cho isolation tối đa nhưng UX kém, và Build-time composition (npm packages) cho simple cases. Trade-offs của MFE: tăng complexity (shared state, routing, styling conflicts, bundle size), cần investment vào platform tooling (shell app, shared libraries, CI/CD), và debugging khó hơn. Migration strategy từ monolith sang MFE nên làm incremental: bắt đầu bằng strangler fig pattern - wrap các features mới trong MFE boundary, dần dần extract existing features, giữ monolith làm shell app ban đầu. Kinh nghiệm của mình ở Caresa HIS: mình chọn monorepo (Turbo) thay vì MFE vì team chỉ có 5-8 người, shared UI nhiều, và không cần independent deployment. Nhưng nếu team grow lên 20+ người với 5 teams độc lập thì MFE sẽ là bước tiếp theo hợp lý.

🇬🇧 **Sample Answer:**
> *"Micro frontends are a powerful pattern, but they're not always the right choice - the complexity cost is real and needs justification. I use a decision framework based on four factors. First, Team Scale: if you have fewer than three frontend teams working on the same product, a well-structured monolith or monorepo is simpler and sufficient. MFE starts making sense when you have five or more teams stepping on each other's toes. Second, Deployment Independence: if teams need to release on different cadences - say the accounts team ships weekly while the payments team ships daily - MFE enables this without coordinated releases. Third, Technology Migration: if you need to incrementally migrate from a legacy framework like AngularJS to React, MFE lets you do this page by page using the strangler fig pattern without a risky big-bang rewrite. Fourth, Organizational Alignment: Conway's Law tells us architecture mirrors team structure, so if your organization is structured around independent product teams, MFE naturally fits. For implementation, I evaluate Module Federation with Webpack 5 or Rspack for runtime composition with shared dependencies, Single-SPA for framework-agnostic orchestration when teams use different frameworks, and build-time composition through npm packages for simpler cases where runtime flexibility isn't needed. The trade-offs are significant: you need to solve shared state management across MFEs, handle cross-MFE routing, prevent CSS conflicts through scoping strategies, manage increased total bundle size from duplicated dependencies, and invest in platform tooling like a shell application and shared component library. For migration from monolith, I recommend the strangler fig approach: start by deploying new features as MFEs while keeping the existing app as the shell, then gradually extract existing features one at a time, validating each step. In my experience at Caresa HIS, I chose a Turbo monorepo over MFE because we had a small team of 5-8 people, heavy shared UI, and no need for independent deployment. But if that team scaled to 20+ engineers across 5 autonomous product teams, MFE would be the logical next evolution."*

## E-02: Architecture Decision - Monorepo Migration

Đây là câu hỏi về technical leadership. Mình dùng STAR format với Caresa HIS monorepo migration. Situation: 5 healthcare apps nằm ở 5 repos riêng, mỗi app có dependencies riêng, UI components không nhất quán, duplicate code nhiều, và TypeScript types không sync giữa các apps. Team 5-8 người mất nhiều thời gian maintain và sync. Task: Là Frontend Lead, mình cần cải thiện developer experience, giảm duplicate code, và đảm bảo consistency across apps. Action: Mình đã research các options (Nx, Lerna, Turbo), chọn Turborepo vì nó nhẹ, caching tốt, và integration với existing tools dễ dàng. Mình tạo migration plan 2 tuần: tuần 1 setup monorepo structure và migrate 2 apps nhỏ trước, tuần 2 migrate 3 apps còn lại. Setup Turbo pipelines cho build, test, lint với remote caching. Result: Build times giảm 60% nhờ Turbo caching, code sharing seamless, onboarding developer mới nhanh hơn 40%, và số TypeScript errors giảm đáng kể vì shared types. The Situation was that each app lived in its own repository with independent dependencies. I wrote an RFC document for the team to review and contribute to, which was important for buy-in. I planned a 2-week migration: week one, I set up the monorepo structure and migrated the two smallest apps to validate the approach; week two, I migrated the remaining three apps. I created three shared packages - @caresa/ui for common components like buttons, modals, and forms with consistent styling; @caresa/utils for shared utilities; and @caresa/api for a type-safe API client with types auto-generated from the backend schema. I configured Turbo pipelines for build, test, and lint with remote caching via Vercel. The Result was significant: build times decreased by 60% thanks to Turbo's caching, code sharing became seamless with a 'change once, use everywhere' workflow, onboarding new developers became roughly 40% faster because there was one repo to clone with consistent patterns, and TypeScript caught integration errors at build time instead of runtime. The team was initially skeptical about the migration effort, but within two weeks of completion, everyone agreed it was the right call."*

## E-03: Performance Optimization - Trading Platform

**Q:** *"Tell me about a time you had to optimize performance. What was the problem, how did you diagnose it, and what was the result?"*

🇻🇳 **Giải thích chi tiết:**
Đây là câu hỏi show kỹ năng technical problem-solving. Mình dùng STAR với Nano Trading platform. Situation: Trading dashboard cần hiển thị 30,000+ records real-time (stock prices, order book, trade history), data update mỗi 100ms qua WebSocket. Initial load mất 8 giây và UI bị jank khi scroll/interact, khiến traders complain vì trong trading, mỗi giây đều quan trọng. Task: Giảm load time xuống dưới 2 giây và đảm bảo UI smooth 60fps khi data update liên tục. Action: Mình bắt đầu bằng profiling - dùng Chrome DevTools Performance tab và React DevTools Profiler để xác định bottlenecks. Phát hiện 3 vấn đề chính: (1) Render 30K DOM nodes cùng lúc - fix bằng react-window virtualization chỉ render 50 visible rows, (2) JSON parsing 30K records block main thread - fix bằng Web Worker để parse và transform data off-main-thread, (3) WebSocket messages trigger re-render mỗi 100ms - fix bằng batching updates với requestAnimationFrame và dùng immutable data structures để React có thể shallow compare hiệu quả. Ngoài ra mình implement connection management - khi tab inactive, giảm WebSocket frequency xuống 1s thay vì 100ms. Result: Load time giảm từ 8s xuống 2s (75% improvement), UI đạt 60fps consistent khi scroll và update, memory usage giảm 40% nhờ virtualization, và traders báo feedback UX smooth hơn nhiều. Bài học: luôn profile trước khi optimize - don't guess, measure.

🇬🇧 **Sample Answer:**
> *"At Nano, I worked on a real-time trading platform where the Situation was critical: our dashboard needed to display over 30,000 records - stock prices, order books, and trade history - with WebSocket updates every 100 milliseconds. The initial load was taking 8 seconds, and the UI was janky during scrolling and interaction. For traders, every second of delay can mean real financial loss, so this was a high-priority issue. My Task was to reduce load time to under 2 seconds and achieve smooth 60fps rendering during continuous data updates. For Action, I started with profiling rather than guessing - I used Chrome DevTools Performance tab to identify long tasks and React DevTools Profiler to find unnecessary re-renders. I identified three major bottlenecks. First, we were rendering 30,000 DOM nodes simultaneously, so I implemented react-window for virtualization, which only renders the 50 or so visible rows plus a small overscan buffer. Second, parsing and transforming 30K JSON records was blocking the main thread for over 2 seconds, so I moved this processing to a Web Worker that returns the transformed data back to the main thread without blocking UI. Third, WebSocket messages were triggering React re-renders every 100ms, so I implemented a batching strategy using requestAnimationFrame to coalesce updates into a single render per animation frame, combined with immutable data structures that enabled React to skip unchanged subtrees via shallow comparison. I also added a smart connection manager that reduced WebSocket frequency from 100ms to 1 second when the browser tab was inactive, saving both bandwidth and CPU. The Result was dramatic: load time dropped from 8 seconds to under 2 seconds - a 75% improvement. The UI maintained consistent 60fps during scrolling and live updates. Memory usage decreased by 40% because virtualization meant we only kept DOM nodes for visible rows. Trader feedback was overwhelmingly positive, and the techniques I documented became standard practices adopted by other teams in the company."*

## E-04: Mentoring Junior Developers

**Q:** *"Tell me about your experience mentoring other developers. How do you approach it?"*

🇻🇳 **Giải thích chi tiết:**

Phase 1 (tuần 1-2): Onboarding - mình tạo comprehensive onboarding doc, pair programming sessions 2h/ngày để họ hiểu codebase architecture, coding conventions, và PR review process. Mình cho họ fix small bugs để làm quen với workflow. Phase 2 (tuần 3-4): Progressive tasks - mình assign features từ nhỏ đến lớn, bắt đầu từ UI components độc lập, rồi đến features có API integration. Mỗi PR mình review chi tiết với explanations, không chỉ "fix this" mà "here's why and here's how to think about it". Phase 3 (tuần 5-6): Independence - họ bắt đầu own features, mình chuyển từ daily pair programming sang weekly 1-on-1 check-ins. Mình cũng tạo "learning budget" - mỗi thứ 6, 2 tiếng để explore new tech hoặc refactor code. Result: Sau 6 tuần, cả 2 bạn đều có thể independently deliver features và review PRs. Bạn junior hơn trở thành go-to person cho UI components, bạn kia own được module API integration. Team velocity tăng vì có thêm người productive. Quan trọng nhất: mình học được rằng mentoring cũng giúp mình improve - khi phải explain concepts, mình hiểu sâu hơn.

🇬🇧 **Sample Answer:**
> *"At Cognisian, the Situation was that we hired two junior developers simultaneously - one fresh graduate and one with about a year of experience - to support our growing Caresa HIS project. They weren't familiar with TypeScript, our monorepo workflow, or the complex healthcare domain. ## E-05: Cross-Geography Collaboration

🇻🇳 **Giải thích chi tiết:**

Situation: Ở dự án KOMO Booking với Eye Design Sydney, mình làm việc với team design và product ở Sydney (UTC+11) và team development ở Vietnam (UTC+7). Task: Đảm bảo collaboration hiệu quả giữa 2 team ở 2 timezone khác nhau, không ai bị block chờ đợi người kia. Action: Mình implement "async-first" communication strategy. Key learning: written communication skills quan trọng hơn verbal khi làm remote/distributed.

🇬🇧 **Sample Answer:**
> *"This is directly relevant to working at ANZ. The Situation was at KOMO Booking where I collaborated with Eye Design in Sydney. The design and product team was in Sydney at UTC+11, while our development team was in Vietnam at UTC+7. The 4-hour timezone difference meant we had only about 3-4 hours of overlap per day - Vietnam afternoon was Sydney early evening. First, every important decision and discussion was documented in writing in Confluence - verbal agreements in calls were always followed up with written summaries, because what isn't written down doesn't exist for a distributed team. Fourth, every pull request included detailed descriptions with screenshots or video demos so reviewers in a different timezone could understand the context without a synchronous conversation. The Result was that we achieved sprint velocity comparable to what you'd expect from a co-located team. Eye Design Sydney gave us feedback that our communication was significantly clearer and more transparent than previous development vendors. ## E-06: Production Incident

**Q:** *"Tell me about a production incident you dealt with. How did you identify and resolve it?"*

🇻🇳 **Giải thích chi tiết:**
Đây là câu hỏi về crisis management và problem-solving under pressure. Situation: Ở Nano Trading, vào một ngày trading bình thường, Sentry bắt đầu báo alert spike - WebSocket connections đang disconnect hàng loạt cho users. Dashboard hiển thị stale data (giá cũ, không update), và traders bắt đầu report qua support. Đây là critical vì stale prices trong trading có thể dẫn đến sai lệch lớn. Task: Xác định nguyên nhân, khôi phục service nhanh nhất có thể, và đảm bảo không xảy ra lần nữa. Action: Mình follow incident response process. Bước 1 - Triage (5 phút): Xem Sentry errors, thấy WebSocket "connection reset" errors tăng 500% trong 10 phút qua. Check server monitoring - server load bình thường, nên vấn đề ở network layer hoặc client-side. Bước 2 - Mitigation (10 phút): Mình dùng feature flag system để switch từ WebSocket real-time sang polling fallback (mỗi 3 giây) - đây là fallback mechanism mình đã build sẵn từ trước. Users bắt đầu nhận data trở lại dù không real-time bằng WebSocket. Bước 3 - Root Cause (1 giờ): Sau khi mitigation xong, mình investigate kỹ hơn. Phát hiện CDN provider đã update SSL certificate và WebSocket connections bị drop vì certificate mismatch. Liên hệ DevOps team coordinate với CDN provider để fix certificate. Bước 4 - Recovery: Sau khi CDN fix, mình toggle feature flag trở lại WebSocket, monitor 30 phút đảm bảo stable, rồi tắt polling fallback. Bước 5 - Post-mortem: Mình viết detailed post-mortem document, identify improvements: thêm certificate expiry monitoring, improve reconnection logic với exponential backoff, và thêm automated health check cho WebSocket connections. Result: Total downtime cho real-time features: 20 phút (từ detect đến mitigation). Zero data loss. Post-mortem dẫn đến 3 infrastructure improvements được implement trong sprint tiếp theo. Team cũng adopt formal incident response playbook.

🇬🇧 **Sample Answer:**
> *"At Nano Trading, the Situation was a sudden production incident during active trading hours. Our monitoring tool Sentry started showing a massive spike in WebSocket disconnection errors - a 500% increase within 10 minutes. Traders were seeing stale prices on their dashboards, which in a trading context is extremely dangerous because decisions based on outdated prices can cause significant financial loss. My Task was to restore data flow as quickly as possible, then find and fix the root cause to prevent recurrence. For Action, I followed a structured incident response. In the first 5 minutes for triage, I checked Sentry error patterns and server monitoring. Server load was normal, which told me the issue was at the network or connection layer, not our application code. For mitigation within the next 10 minutes, I used our feature flag system to switch all users from WebSocket real-time streaming to a polling fallback that fetched data every 3 seconds. Users immediately started receiving fresh data again - not as fast as WebSocket, but functional and safe. With the immediate crisis mitigated, I spent the next hour on root cause analysis. I traced the issue to our CDN provider, which had rotated their SSL certificate, causing a certificate mismatch that dropped all persistent WebSocket connections. I coordinated with our DevOps team to contact the CDN provider and resolve the certificate configuration. Once confirmed fixed, I toggled the feature flag back to WebSocket, monitored for 30 minutes to ensure stability, then fully deactivated the polling fallback. The total real-time feature disruption was about 20 minutes from detection to mitigation, with zero data loss throughout. After the incident, I led a post-mortem that resulted in three concrete improvements: we added automated certificate expiry monitoring with 30-day advance alerts, I enhanced the WebSocket client with exponential backoff reconnection logic, and we implemented automated health checks that would trigger the polling fallback automatically without manual intervention. The team also adopted a formal incident response playbook based on this experience, which has been used successfully in subsequent minor incidents."*

## E-07: Handling Technical Debt

**Q:** *"How do you balance delivering new features with addressing technical debt? Can you give me a specific example?"*

🇻🇳 **Giải thích chi tiết:**
Đây là câu hỏi về pragmatism và engineering maturity. Situation: Ở Caresa HIS, sau 1 năm phát triển nhanh, codebase tích tụ technical debt đáng kể: một số components có 500+ lines không có tests, API layer dùng mix giữa fetch và axios không nhất quán, và state management có chỗ dùng Redux, có chỗ dùng Context, có chỗ dùng local state không có pattern rõ ràng. Junior developers bắt đầu complain khó hiểu code và bug rate tăng. Task: Giảm technical debt để cải thiện developer experience và code quality, nhưng không được stop feature delivery vì business commitments vẫn tiếp tục. Action: Mình tạo "Technical Debt Prioritization Matrix" với 2 axes: Impact (ảnh hưởng đến tốc độ development và bug rate) và Effort (thời gian cần để fix). Chia thành 4 quadrants: High Impact/Low Effort (làm ngay - quick wins), High Impact/High Effort (plan vào sprint), Low Impact/Low Effort (làm khi có thời gian), Low Impact/High Effort (không làm hoặc để sau). Rồi mình áp dụng "Boy Scout Rule" - mỗi PR phải để code tốt hơn lúc mình vào. Cụ thể: mình negotiate với Product Owner dành 20% mỗi sprint cho tech debt (2 ngày trong sprint 2 tuần). Bắt đầu với quick wins: standardize API layer sang TanStack Query (High Impact, Medium Effort - 3 ngày), sau đó refactor state management sang pattern nhất quán (Zustand cho global, TanStack Query cho server state). Mỗi refactoring được làm alongside features - ví dụ khi build feature mới cho module billing, mình refactor billing components luôn thay vì chỉ thêm code mới lên code cũ. Mình track debt reduction metrics: số lượng components có tests, code coverage, và số bug reports liên quan đến refactored modules. Result: Sau 3 tháng, code coverage tăng từ 30% lên 65%, bug rate giảm 40%, và developer satisfaction survey cho thấy team happy hơn với codebase. Quan trọng: mình luôn frame tech debt reduction bằng business value - "giảm bug rate" thay vì "refactor code" khi nói với Product Owner.

🇬🇧 **Sample Answer:**
> *"At Caresa HIS, the Situation was typical of a product after a year of rapid feature development. We had accumulated significant technical debt: some components exceeded 500 lines without tests, the API layer inconsistently mixed fetch and axios, and state management had no clear pattern - some features used Redux, others used Context, others used raw local state. Junior developers were struggling to understand the codebase, and our bug rate was increasing sprint over sprint. My Task was to reduce this debt while continuing to deliver features - business commitments didn't pause for refactoring. For Action, I created a Technical Debt Prioritization Matrix with two axes: Impact on development velocity and bug rate, and Effort required to fix. This gave us four quadrants: High Impact/Low Effort as immediate quick wins, High Impact/High Effort as planned sprint work, Low Impact/Low Effort as opportunistic improvements, and Low Impact/High Effort as deferred or never-do items. I negotiated with our Product Owner to allocate 20% of each sprint - roughly 2 days in a 2-week sprint - specifically for technical debt reduction. I framed this in business terms: 'reducing our bug rate' and 'increasing feature delivery speed' rather than 'refactoring code,' which made it much easier to get buy-in. I started with quick wins: standardizing the API layer to TanStack Query, which eliminated inconsistency and gave us caching and error handling for free. Then I tackled state management, establishing clear patterns - Zustand for global client state, TanStack Query for server state, URL params for navigation state. Crucially, I paired refactoring with feature work: when we built new billing features, we refactored the billing module's existing components in the same sprint, so the improvement was incremental rather than a separate 'refactoring sprint' that delivered no visible value. I tracked debt reduction through concrete metrics: test coverage percentage, bug report count per module, and time-to-implement for new features in refactored versus non-refactored modules. The Result over three months was measurable: test coverage increased from 30% to 65%, bug rate dropped 40%, and our developer satisfaction survey showed the team was significantly happier with the codebase quality. The most important lesson was that technical debt is best addressed continuously alongside feature work, not in big-bang refactoring sprints that are hard to justify and risky to execute."*
